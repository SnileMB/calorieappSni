<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user input → Supabase Auth | Email/password strings cross from an untrusted form into GoTrue |
| browser localStorage → app | The persisted JWT lives in localStorage and is readable by any script on the origin |
| authenticated client → `public.profiles` | Every profile read/write crosses into the database and is scoped only by RLS |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-09 | Spoofing | Auth mechanism | mitigate | Email/password via Supabase Auth only (SYNC-02); `signInAnonymously` absence enforced by the automated guard test from plan 01-01 |
| T-01-10 | Information Disclosure | Auth error rendering | mitigate | `toUserMessage` collapses "invalid credentials" and "already registered" to one identical message, so sign-up/log-in errors cannot be used to enumerate which emails have accounts; raw Supabase text never reaches the DOM |
| T-01-11 | Information Disclosure | Cross-user profile read | mitigate | Enforced by the RLS policies pushed in plan 01-02, not by client-side filtering; `profileApi` deliberately contains no app-layer authorization check to avoid implying one exists |
| T-01-12 | Session hijacking / Elevation of Privilege | JWT in localStorage | accept | Standard supabase-js default for a SPA with no SSR (CONTEXT.md D-01 rules out SSR, so the cookie adapter is not applicable). Single-user private app, no XSS-injecting third-party scripts, no runtime-cached API responses (plan 01-05 precaches static assets only). Accepted risk, documented here |
| T-01-13 | Tampering | Stale session after sign-out | mitigate | `AuthProvider` derives all state from `onAuthStateChange`; `signOut()` fires the event so the UI cannot keep rendering authenticated content against a revoked session. Verified by Task 3 step 11 |
| T-01-14 | Cryptography (delegated) | Password handling | transfer | Hashing/verification is entirely Supabase Auth (GoTrue) server-side; no password ever touches app storage or logs |
</threat_model>
